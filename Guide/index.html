01

Overview

You're building a 2D top-down racing simulator and an AI that learns to drive it through reinforcement learning. The simulator is in TypeScript; the AI lives in Python; a thin protocol connects them.

The key idea behind this split: the simulator only has to know how to be a world. It doesn't know what algorithm is driving — DQN today, PPO or imitation learning tomorrow. That's why every algorithm-specific concept (replay buffers, optimizers, reward shaping) lives behind the protocol boundary in Python.

What you'll build, in order

  1. A 2D simulator with realistic-ish car physics — bicycle model, slip angles, RWD power oversteer.
  2. An observation pipeline — what the agent perceives every frame: ray distances, kinematics, slip, lap progress.
  3. A discrete action table — seven combinations of throttle / brake / steer the agent can pick from.
  4. A protocol between TS and Python so the simulator and the brain are loosely coupled.
  5. A Deep Q-Network that maps state vectors to Q-values for each action.
  6. A reward function in Python that turns simulator transitions into learning signal.
  7. A training loop that runs many episodes, stores experience, and improves the network.
Why this order

The world has to be solvable and stable before there's any point pointing a learner at it. A bad sim teaches a good algorithm garbage — and you'll spend weeks blaming the algorithm. So: physics first, then RL.

02

The Simulator

The simulator advances the world in fixed-size time steps. Same dt every step, no matter the wall clock. This makes physics deterministic and reproducible — the same action sequence on the same track always produces the same trajectory.

// src/domain/simulation.ts
export const DEFAULT_SIM_CONFIG: SimConfig = {
  fixedDt: 1 / 60,   // 60 ticks per second
  // ...
};

Car state

The car is a small struct. Position, heading, velocity (in world coordinates), and now also yaw rate — the angular velocity of the chassis. We'll need that the moment we move beyond a point-mass model.

interface CarState {
  x: number;
  y: number;
  heading: number;   // radians, atan2 convention
  vx: number;        // world-frame velocity
  vy: number;
  yawRate: number;   // angular velocity (rad/s)
  // lap tracking, collisions, etc.
}

Step function

Every tick, stepSimulation takes the current state and an action and returns the next state. It's a pure function — no hidden globals, no time-of-day randomness. RL training depends on this purity.

function stepSimulation(
  state: SimulationState,
  action: AgentAction,         // throttle, brake, steer (all in [-1, 1] or [0, 1])
  track: CompiledTrack,
  dt: number
): SimulationState;

03

Bicycle-Model Physics

Most arcade racers model the car as a single point: one position, one velocity, one heading. Steering instantly rotates the car; lateral friction instantly aligns velocity with heading. It's simple, but the car has no character — it can't slide, can't oversteer, can't lose grip. You can never "lose the back end."

The bicycle model upgrades this by giving the car two axles — one front (steers), one rear (drives) — connected by a chassis. Each axle has its own velocity, its own slip angle, its own lateral force. The car's heading is now driven by moment (a torque around the center of mass), not by the steering input directly.

Slip angle: the heart of the model

A tire's slip angle is the angle between the direction the tire is pointing and the direction it's actually moving. If they're aligned, no slip. If they differ, the tire deforms and pushes back — that's the lateral force that makes the car turn.

For the bicycle model, with body forward velocity vbx, body lateral velocity vby, yaw rate r, and front-wheel steering angle δ:

slipFront = δ - (vby + a · r) / vbx
slipRear  =   - (vby - b · r) / vbx

Read those: the front-axle slip is where you pointed it minus where it's actually heading. The rear has no steering input, so its slip is purely "the rear is rotating off the velocity vector."

Yaw rate as state

In a point-mass sim, yaw rate doesn't exist — heading is just whatever the steering input says. In a bicycle model, yaw rate has its own dynamics: it changes when the front and rear lateral forces produce different moments around the CoM. This is what "the car has inertia" actually means.

// Moment around CoM (positive = counter-clockwise yaw acceleration)
moment = a · F_front_lateral - b · F_rear_lateral

// Newton's second law for rotation
yawRate += (moment / yawInertia) · dt
heading += yawRate · dt

If front grip exceeds rear grip during a corner, the rear rotates out — oversteer. If rear grip exceeds front grip, the car plows wide — understeer. Both fall out of the equations naturally; you don't have to script either.

04

Tire Forces & RWD

Once you have a slip angle, you need to turn it into a force. Real tires are nonlinear: at small slip the force grows almost linearly with slip; past a certain point the rubber starts sliding and the force caps. That cap is the tire's peak grip.

We use a tanh-shaped curve, not a hard clamp. Two reasons:

  • Smooth gradients. Neural-network value approximators (DQN, PPO, etc.) hate sharp cliffs. tanh is differentiable everywhere; a clamp has a corner at the saturation point that the network has to spend capacity learning to fit.
  • It matches reality. Real tires soften their grip near the limit too — they don't go from full grip to zero grip in one slip-angle increment.
// Linear-region stiffness, saturating to peak grip
const fyFront = tireGripFront *
  Math.tanh((stiffnessFront * slipFront) / tireGripFront) *
  speedFactor;

speedFactor = tanh(|v| / 30) kills the slip-derived forces at low speed, where the slip-angle math becomes ill-defined (you can't have a slip angle on a stationary tire).

RWD via the friction circle

A real tire has a single friction budget shared between longitudinal force (driving / braking) and lateral force (cornering). Push it hard one direction and there's less left for the other. This is the friction circle:

F_long² + F_lat² ≤ peak²

For a rear-wheel-drive car, the engine puts longitudinal force at the rear axle. So when you stomp the throttle, the rear tire's available lateral grip drops. Combine that with any cornering — and the rear breaks loose. That's power oversteer.

// Rear axle eats engine force out of its grip budget (RWD)
const rearLongUsed = Math.min(Math.abs(engineLong), tireGripRear);
const rearLatBudget = Math.sqrt(
  Math.max(0, tireGripRear ** 2 - rearLongUsed ** 2)
);
// Lateral tire force is now capped by what's LEFT after longitudinal demand
const fyRear = rearLatBudget * Math.tanh(...);
Watch out

Sign conventions are the most common bug source in vehicle physics. Tire force should always oppose slip — if a positive slip produces a positive force in the same direction, you've created a positive feedback loop and your car will spin uncontrollably the moment any disturbance enters the system.

05

Track, Checkpoints, Rays

The track is a closed centerline (a list of 2D points) with a width per segment. Internally it gets compiled into segments with cumulative arc lengths so we can ask "how far around the lap am I?" cheaply.

Checkpoints

Lap detection has to handle a car that partially goes around — you don't want progress that suddenly jumps backwards because the car cut a corner. Checkpoints are progress markers placed around the track. The car has to cross them in order, and only after crossing them all does a lap count.

Rays — vision via raycasting

The car doesn't see the world as pixels. Instead, it casts rays outward from itself and measures the distance to the nearest off-track point in each direction. This gives a low-dimensional, view-rotation-invariant snapshot of the local geometry — perfect for a small neural network.

The ray angles are configurable but default to fanning across roughly ±90° from the car's nose. Each ray returns a single number: distance to the nearest track edge along that direction, or the max-distance value if it never hits one. With nine rays plus a few scalar fields, the agent can navigate without ever knowing where it is on a global map.

06

Observation & State Vector

An AgentObservation is everything the agent could possibly want to know about the world this frame, in a structured shape. It then gets encoded into a flat normalized array — the state vector — which is what actually feeds the neural network.

interface AgentObservation {
  rays: number[];           // 9 raw ray distances
  speed: number;            // |v|
  yawRate: number;          // chassis angular velocity
  bodySlipAngle: number;    // atan2(vby, vbx) — "how sideways am I?"
  headingError: number;     // angle between heading and track tangent
  lateralOffset: number;    // signed distance from track centerline
  lapProgress: number;      // 0..1, normalized arc-length around the lap
  offTrack: boolean;
  collision: boolean;
  // ...
}

Why each field exists

  • rays — local geometry. Without these the agent can't see walls coming.
  • speed — pretty obvious; affects how fast everything else is changing.
  • yawRate — required by the bicycle model. Without it, "going straight at 200" and "spinning at 200" are the same observation. DQN sees one frame at a time and would never recover from a spin.
  • bodySlipAngle — distinguishes "going forward" from "sliding sideways." Critical for an oversteer-prone car.
  • headingError — points the agent toward the right racing direction.
  • lateralOffset — keeps it honest about staying near the racing line.
  • lapProgress — encoded as sin(2π · lapProgress), cos(2π · lapProgress) so it wraps continuously around 1.0 → 0.0 with no discontinuity.

The state vector — a fixed contract

The neural network needs a fixed-size array of normalized floats, every frame, forever. Once you commit to a layout, you commit to it — old trained models depend on the exact ordering and scaling. So we version it.

// src/domain/ai/encodeObservation.ts
export const STATE_VECTOR_VERSION = 2;
export const STATE_VECTOR_SIZE = 18;
export const MAX_YAW_RATE = 6;

export function encodeObservation(obs: AgentObservation, config = DEFAULT_SIM_CONFIG): number[] {
  const lapAngle = obs.lapProgress * Math.PI * 2;
  return [
    ...obs.rays.map((r) => clamp(r / config.rayMaxDistance, 0, 1)),
    clamp(obs.speed / config.maxSpeed, 0, 1),
    clamp(obs.headingError / Math.PI, -1, 1),
    clamp(obs.lateralOffset / 2, -1, 1),
    Math.sin(lapAngle),
    Math.cos(lapAngle),
    obs.offTrack ? 1 : 0,
    obs.collision ? 1 : 0,
    clamp(obs.yawRate / MAX_YAW_RATE, -1, 1),
    clamp(obs.bodySlipAngle / (Math.PI / 2), -1, 1),
  ];
}
Versioning matters

If you ever change the state vector — adding a field, reordering, changing a normalization constant — bump STATE_VECTOR_VERSION. Old saved models trained against the old layout will be silently wrong otherwise. The Python side should refuse a session whose version doesn't match what the model expects.

07

Discrete Action Space

DQN learns a Q-value for every (state, action) pair. With continuous actions (any throttle from 0 to 1, any steer from −1 to 1) the action space is infinite — you can't argmax over infinity. So we discretize: a small fixed table of (throttle, brake, steer) triples, indexed 0…N.

export const AI_ACTIONS: AgentAction[] = [
  { throttle: 0.85, brake: 0,    steer:  0     },  // 0: full ahead
  { throttle: 0.75, brake: 0,    steer: -0.45  },  // 1: gentle left
  { throttle: 0.75, brake: 0,    steer:  0.45  },  // 2: gentle right
  { throttle: 0.35, brake: 0,    steer: -0.8   },  // 3: tight left
  { throttle: 0.35, brake: 0,    steer:  0.8   },  // 4: tight right
  { throttle: 0,    brake: 0.65, steer:  0     },  // 5: brake
  { throttle: 0.12, brake: 0.25, steer:  0     },  // 6: trail-brake / settle
];

Why these seven?

It's a sweet spot. Each action expresses a different intent: cruise, ease into a corner, commit to a tight corner, slow down, recover from instability. With three steering levels per throttle setting and a brake row, the agent can race a clean lap with this minimal table.

Could you use 30 actions? Sure — and the Q-network gets a wider output layer. But more actions also means more entries the network has to learn correct relative values for, which slows learning. Start with 7. Expand only if you observe the agent visibly struggling for nuance the table can't express (e.g. cornering on the limit).

The contract

Python returns action indices, never raw throttle / brake / steer. The simulator owns the lookup. This keeps the protocol tiny, lets multiple algorithms share the same action space, and means the action table version is the only thing you have to negotiate.

Looking ahead

If you later move to PPO or SAC (continuous-action algorithms), the protocol can keep the action-index path for DQN and add a parallel raw-action path. Don't refactor pre-emptively — wait until you actually need it.

08

TS ↔ Python Protocol

The simulator and the brain talk over WebSocket. WebSocket is a good fit because we send dozens of small messages per second per simulator instance — HTTP overhead would dominate.

Three message types

1. Session start

The first thing TS sends. It tells Python what kind of world this is — protocol versions, vector size, time step, action count. Python compares these to what its model expects and either accepts or rejects.

{
  "type": "session_start",
  "sessionId": "run-001",
  "trackHash": "abc12345",
  "stateVectorVersion": 2,
  "actionSpaceVersion": 1,
  "fixedDt": 0.0166666667,
  "stateSize": 18,
  "actionCount": 7
}

2. Action request

Every simulator step (or every Nth step), TS sends the current state and Python returns the index of the action to execute.

// TS → Python
{ "type": "action_request", "step": 128, "state": [0.81, 0.74, ...] }

// Python → TS
{ "type": "action_response", "step": 128, "actionIndex": 2 }

3. Transition

After TS applies the action and steps physics, it sends the resulting transition. Python computes reward from this and stores the transition in its replay buffer.

{
  "type": "transition",
  "step": 128,
  "state": [...],
  "actionIndex": 2,
  "nextState": [...],
  "done": false,
  "env": {
    "previousProgressDistance": 312.4,
    "nextProgressDistance": 319.8,
    "totalLength": 1840.2,
    "speed": 196.6,
    "collision": false,
    "offTrack": false,
    "lapCompleted": false,
    "elapsed": 2.15
  }
}

The env sub-object is the raw simulator data Python needs to compute reward — not the normalized state vector, since reward is most cleanly defined in real units (px/s, px of progress, etc.).

Why this design

State, action, reward, next state — that's literally a transition in the RL sense. The protocol is shaped to give Python exactly what it needs to add a row to its replay buffer. Nothing more, nothing less.

09

DQN: How It Learns

DQN — Deep Q-Network — learns a function Q(s, a): "if I'm in state s and take action a, what total future reward should I expect?" Once you can estimate that, picking the best action is just argmax_a Q(s, a).

The Bellman equation

The whole framework rests on one recursive identity: the value of a state-action pair equals the immediate reward plus the discounted value of where you'll end up next.

Q(s, a) = r + γ · max_a' Q(s', a')

γ ∈ [0, 1) is the discount factor — how much we care about future reward vs. immediate. γ = 0.99 is a typical choice; it means the reward 100 steps from now is worth about 37% as much as reward right now.

From equation to network

For a tiny problem (gridworld), Q is just a table indexed by (state, action). For our problem the state space is continuous and 18-dimensional — way too big for a table. So we approximate Q with a neural network: input = state vector (18), output = one Q-value per action (7).

input:  18  (state vector)
dense:  64, ReLU
dense:  64, ReLU
output:  7  (one Q-value per action)

Three tricks that make DQN actually work

If you naively train a Q-network on every transition as it arrives, learning is unstable: consecutive transitions are highly correlated, the targets you're regressing toward shift while you're regressing, and rare events get drowned out. DQN solves this with three additions:

1. Replay buffer

Store the last N transitions in a big circular buffer. Train on random minibatches sampled from it. This breaks the correlation between consecutive frames and lets the network revisit rare events many times.

replay_buffer.push(state, action_index, reward, next_state, done)
batch = replay_buffer.sample(batch_size=64)

2. Target network

The Bellman equation has Q on both sides. If you use the same network on both — predicting and setting the target — you're chasing a moving target, which is unstable. So you keep two copies: an online network you train every step, and a target network whose weights you hard-copy from online every K steps. The target network sets the right-hand-side of Bellman:

td_target = reward + (0 if done else gamma * target_net(next_state).max())
loss = (online_net(state)[action_index] - td_target) ** 2

3. ε-greedy exploration

Early in training, the Q-values are random — the argmax is meaningless. You need to explore. With probability ε, take a random action; otherwise take the argmax. ε starts near 1.0 and decays toward something like 0.05 over the course of training.

if random.random() < epsilon:
    action_index = random.randrange(action_count)
else:
    action_index = q_network(state).argmax()
Three knobs to keep an eye on

γ too low → agent is short-sighted, refuses to brake before corners. ε decay too fast → agent commits to a bad early policy. Target update period too short → instability; too long → slow learning.

10

Reward Design

Reward is the only signal the agent has about what you actually want. If your reward function is wrong, the agent will learn to maximize the wrong thing — and it'll do it very effectively. This is the most-edited file in any RL project, by a wide margin.

A reasonable starting reward

progress_reward    =  progress_delta_px * 0.02
speed_reward       =  speed              * 0.0008
steering_penalty   =  abs(action.steer)  * 0.01
collision_penalty  =  2.0  if collision     else 0.0
off_track_penalty  =  0.12 if off_track     else 0.0
stuck_penalty      =  0.02 if speed < 12   else 0.0
lap_bonus          =  8.0  if lap_completed else 0.0

reward = (
    progress_reward + speed_reward + lap_bonus
    - steering_penalty - collision_penalty - off_track_penalty - stuck_penalty
)

Why each term

TermWhy
progress The headline goal. Agent gets paid by the meter for moving forward around the track. Computed from nextProgressDistance − previousProgressDistance, with wrap-around handling at the start line.
speed Small constant nudge to keep moving. Without this, the agent learns that creeping carefully forward earns the same per-step progress reward as charging — but with less risk of crashing. Speed reward breaks that tie.
steering penalty Discourages flailing. Without it, agents often learn jittery zigzag policies that maximize average progress but look terrible.
collision / off-track The fence. Without these the optimal policy involves bouncing off walls.
stuck penalty Rescues episodes where the agent has spun out and is sitting still. Forces it to do something.
lap bonus A big sparse reward when the agent actually completes the goal. Often the difference between "agent corners well" and "agent races."

Common reward bugs

  • Reward sign wrong on progress wrap-around. When the car crosses the start line, raw progressDistance jumps from totalLength to 0, which looks like a giant negative delta. Always clamp progress delta to a reasonable forward range, and award the lap bonus separately.
  • Reward magnitudes too uneven. If collision_penalty is huge compared to per-step progress reward, the agent will learn extreme avoidance — even if that means refusing to drive.
  • Rewarding what's easy to measure instead of what you want. "Stay near centerline" sounds reasonable until your agent learns to drive painfully slowly along the centerline forever. Always ask: does the optimal cheating policy achieve my real goal?
Specification gaming is real

If there's a way to maximize your reward without doing what you intended, the agent will find it. Reward design is half engineering, half adversarial — assume your function will be exploited and ask how.

11

Training Loop

Now we put everything together. There's a per-step loop and an outer episode loop.

# Once per simulator step
state = encode_observation(obs)
action_index = epsilon_greedy(q_network, state, epsilon)
send_action(action_index)

transition = wait_for_transition()
reward = compute_reward(transition)
replay_buffer.push(state, action_index, reward,
                   transition.next_state, transition.done)

# Every K steps, after warmup
if step > warmup_steps and step % train_every == 0:
    batch = replay_buffer.sample(batch_size)
    train_step(online_net, target_net, batch, gamma, optimizer)

if step % target_update_every == 0:
    target_net.load_state_dict(online_net.state_dict())

Live mode vs. headless mode

The same protocol supports two clients:

  • Live mode — the React app renders the game, the user can watch the agent drive. Useful for inspecting behavior. Limited to ~60 steps per second by the renderer.
  • Headless mode — a pure-TS runner steps the simulator as fast as possible with no rendering. Used to actually generate the experience that DQN trains on. Often 10× to 100× faster than live mode.

Don't try to train on live mode. Use it for debugging only. Real training runs need the throughput of headless.

Starting hyperparameters

gamma                    = 0.99
learning_rate            = 0.00025
batch_size               = 64
replay_capacity          = 50_000
warmup_steps             = 2_000   # fill the buffer before training
train_every_steps        = 4
target_update_every      = 1_000
epsilon_start            = 1.0
epsilon_end              = 0.05
epsilon_decay_steps      = 40_000

These aren't sacred. Tune them when something is clearly wrong (loss exploding → lower learning rate; agent stuck random → faster epsilon decay; etc.). Don't tune them preemptively.

12

Debugging & Next Steps

If behavior looks wrong

  • Verify TS and Python agree on stateVectorVersion. A version mismatch silently shifts every input feature.
  • Verify actionSpaceVersion. Same problem on the action side: index 2 means different things.
  • Log every action index and the decoded action. If "left" turns produce right-hand cornering, you have a sign or index mismatch.
  • Check finite values. The bicycle model's slip-angle math has vbx in the denominator; very-low-speed states are the most common NaN source if anyone removes the low-speed force fade.
  • Random policy first, always. Before plugging in DQN, run a uniform-random Python policy and confirm the car moves and produces transitions. If that doesn't work, the bug isn't in your learner.
  • Compare live and headless transitions. They should be byte-identical given the same seed and action sequence.
  • Watch the loss. Q-loss should drop steadily and then plateau. Exploding loss = lower learning rate or smaller gradient clipping. Flat-zero loss = your TD targets aren't moving (broken target network update? broken sampling?).

Sanity benchmarks

  • Random policy should achieve some non-zero average progress per episode (it'll occasionally face the right way and accelerate). If it doesn't, your physics or your reward is broken.
  • DQN after 100K steps should clearly beat random average progress. If it's the same, something's not learning.
  • DQN after 1M steps on a simple track should complete laps reliably. If it can't, you're either under-exploring or your reward shaping is fighting you.

Beyond DQN

The protocol was designed so that the simulator doesn't know which algorithm is on the other end. That means once DQN works, you can swap in:

  • PPO (Proximal Policy Optimization) — continuous actions, better sample efficiency, more stable. The mainstream choice for continuous control as of the late 2020s.
  • SAC (Soft Actor-Critic) — also continuous, off-policy. Often even more sample-efficient than PPO.
  • Imitation learning — record human (or hand-crafted) drives, train the network to copy them. A great way to bootstrap: fine-tune with RL on top.
  • Reference-clone agents — the rule-based ReferenceLineAgent in the codebase doesn't learn, but you can use its actions as expert demos for imitation pretraining.

What to build next, in order

  1. Make sure the simulator produces stable, fast, deterministic transitions.
  2. Build the protocol with a random Python policy. Verify round-tripping.
  3. Move reward computation into Python; verify the numbers look reasonable.
  4. Build the headless TS runner.
  5. Implement DQN. Train on a simple oval first.
  6. Iterate the reward function as the agent finds new ways to surprise you.
  7. Add evaluation runs (greedy, no exploration) on a held-out track to detect overfitting.
You're done when

The React app can drive from Python's actions. A random policy can run complete episodes through your protocol. The headless runner generates faster-than-real-time transitions. DQN training shows monotonically rising average progress over random. And the protocol is generic enough that adding a second algorithm doesn't require touching the simulator.
